Section A تحليل المتطلبات

Requirements Analysis

What the brief already specifies, organized so the rest of this document can build on it without re-litigating it.

Non-negotiable constraints

Deployment
Windows PC · XAMPP (Apache + PHP + MySQL/MariaDB) · copy-to-htdocs install.
Connectivity
Must run with internet fully disabled, indefinitely, after install. No CDNs, no external APIs, no SaaS.
Frontend
HTML5 / CSS3 / vanilla JS + Bootstrap + jQuery where it earns its place — all vendored locally.
Backend
PHP with PDO + prepared statements only. No raw string-built SQL, ever.
Language
Arabic-first, RTL by default; English/LTR as a full secondary mode — not a mirrored afterthought.
Users
Non-technical school staff. Plain-language messages, confirmations, empty states — no jargon.
Scale
Must stay fast with thousands of student records — indexed queries, pagination, no N+1s.
Data safety
Student/teacher history is never overwritten; promotions and restores are transactional and reversible.

The twelve functional pillars

Students · Teachers · Grades · Classes · Subjects · Teacher↔class assignments · Weekly teaching load · Statistics · Reports (print/PDF/Excel) · Backup & restore · Academic-year transitions · Administrative settings.

Cross-cutting requirements

  • Authentication & roles — hashed passwords, sessions, login throttling, at minimum Administrator and Staff roles, enforced server-side.
  • Activity log — every consequential action (login, create/edit/archive, promotion, backup, restore) recorded with actor, entity, and timestamp.
  • Reports are real — generated from live database queries, never faked or computed client-side in JavaScript.
  • Backup is one-click, timestamped, with a safe, guarded restore path that never touches the live database without an emergency backup first.
  • First-run setup wizard — school identity, first academic year, admin account, seed subjects/grades — no manual database editing for normal setup.
  • Configurable business rules — expected weekly teaching load, staffing-shortage thresholds, ID formats — stored in settings, not hardcoded in PHP.
Section B قرارات معلقة

Missing & Ambiguous Decisions

Fourteen decisions the brief leaves open, each with a recommendation and a reason. All fourteen are now confirmed — #6 was settled directly by the client on 2026-09-06 (single school per installation); the other thirteen proceed on the stated recommendation per the brief's own rule (item 40).

1 · Backend architecture style

Proceeding
Recommend
A hand-rolled, lightweight MVC — front controller, router, Composer PSR-4 autoloading — not Laravel/Symfony.
Reason
A full framework brings artisan/queue/cache assumptions and a much heavier vendor tree, which fights the "just copy to htdocs" promise. A slim custom MVC gives the same separation of concerns (controllers → services → repositories) with a footprint that's just PHP files behind Apache.
Alternative
Laravel — more built-in tooling (migrations, Eloquent, Blade), at the cost of deployment simplicity for a school running unmanaged XAMPP.

2 · Composer / vendor policy

Proceeding
Recommend
Use Composer during development only; ship the populated vendor/ folder in the delivered package.
Reason
Needed for mPDF / PhpSpreadsheet / a small logger without ever asking the school to run composer install or touch the internet.
Alternative
Hand-vendor each library's source directly — no autoload discipline, harder to update later.

3 · PDF export engine

Proceeding — refined by audit §O-15
Recommend
mPDF — pure PHP, strong Arabic shaping/RTL, embeddable fonts (e.g. Amiri, Noto Naskh Arabic), no shell dependency.
Reason
Reports must render correct Arabic completely offline; mPDF is the most mature pure-PHP option for Arabic script shaping and justification.
§O-15 concrete deliverable
"mPDF has RTL support" is not, by itself, a guarantee — mPDF ships with a limited default font set, and without explicit action it silently falls back to a non-Arabic-capable font (boxes/tofu instead of glyphs). The blueprint now names the exact asset: Amiri-Regular.ttf and Amiri-Bold.ttf bundled under vendor-assets/fonts/ and registered in mPDF's font configuration — this is a checklist item for Phase 7, not an assumption baked into the library choice.
Alternative
TCPDF — also RTL-capable, more verbose API. Dompdf — weaker Arabic support, not recommended for this project.

4 · Excel export engine

Proceeding
Recommend
PhpSpreadsheet — de-facto standard, pure PHP, supports RTL sheet direction and cell styling.
Reason
Produces genuine .xlsx files with formatting, not a lossy CSV dump.
Alternative
Plain CSV — trivial to generate, but loses formatting, RTL direction, and the "professional report" feel the brief asks for.

5 · Charting library

Proceeding
Recommend
Chart.js, vendored as a single local file.
Reason
Canvas-based, no build step, easy to theme, small enough to commit directly.
Alternative
ApexCharts — nicer defaults, heavier payload; hand-rolled SVG — more control, more development time for no real gain here.

6 · Single school vs. multi-branch

Confirmed 2026-09-06
Ambiguity
The dashboard spec asks for student breakdowns "by school," which could mean one school per install (most likely) or one install serving several campuses.
Decision
One school per installation, confirmed directly by the client. The schools table still exists (single active row, created once by the Setup Wizard) so the "by school" dashboard stat and the school name/logo on printed reports have somewhere to live — it is not a multi-tenant feature, just a profile record.
Effect on §D
No school_id foreign key threading through students/classes/teachers — every table's scoping stops at academic_year_id. This is the schema actually built out in §D below.

7 · Authorization granularity

Proceeding
Recommend
Build the full roles / permissions / role_permissions schema now, but seed only Administrator and Staff with a fixed, code-defined permission checklist — not a drag-and-drop permission builder.
Reason
Satisfies the brief's explicit permissions table requirement while keeping v1's UI surface (and QA burden) proportionate.
Alternative
A full custom permission-matrix screen — more flexible, meaningfully more UI and testing for a first release.

8 · Backup engine

Proceeding
Recommend
A pure-PHP dump routine (streaming table reads → SQL statements), not shelling out to mysqldump.exe.
Reason
shell_exec() is often disabled by hardened PHP configs, and the XAMPP binary path varies by version — a pure-PHP dumper removes that entire failure class.
Alternative
shell_exec("mysqldump ...") — faster on very large databases, but fragile path detection and requires exec() permissions an admin may have locked down.

9 · Restore engine

Proceeding
Recommend
Parse and replay the uploaded .sql file in-app, batched, always preceded by an automatic emergency backup — never "go import it in phpMyAdmin."
Reason
Keeps restore inside the same confirmation / activity-log / rollback-messaging safety net as everything else.
Alternative
Point the admin at phpMyAdmin — simpler to build, but breaks the "safe, one-click, in-app" promise and drops the emergency-backup guarantee.

10 · Student / teacher ID format

Proceeding — refined by audit §O-7
Recommend
Auto-generated, human-readable codes — STU-2025-000118, TCH-000045 — pattern configurable in Settings.
Reason
Staff need something they can write on a physical form or register; a raw auto-increment ID isn't meaningful to them.
Generation (corrected)
The audit caught a race condition in the original plan: computing the next number as MAX(seq)+1 in PHP is unsafe if two staff save a new student at the same moment. Corrected mechanism: insert the row first, letting MySQL's own AUTO_INCREMENT assign the primary key atomically, then UPDATE that same row's student_code using the now-known id — e.g. row id 118 becomes STU-2025-000118. No separate counter table, no race.
Year component
The year in the code is the year the record was created, not a per-year-resetting sequence — numbers keep climbing across years (…000118, 000119, 000120 regardless of year boundary). Simpler and race-free.
Alternative
A numbering scheme that resets to 1 every academic year, if the school specifically wants that — requires a dedicated id_sequences counter table with SELECT ... FOR UPDATE row locking per year. More familiar to some registrars, meaningfully more implementation and testing surface for a v1.

11 · Photo / logo storage

Proceeding — hardened by audit §O-18
Recommend
Local disk under /storage/uploads/<type>/, strict MIME + extension whitelist, images re-encoded on upload.
Reason
Offline-only by nature, and re-encoding neutralizes disguised-executable upload attacks.
§O-18 added hardening
Re-encoding alone isn't defense in depth. Three more layers: (1) stored files get a randomly-generated filename, never the name the browser sent; (2) a controller streams the file back with an explicitly-set Content-Type rather than letting Apache guess from the extension; (3) the uploads folder carries an .htaccess that disables PHP execution (php_flag engine off), so even a file that somehow bypassed re-encoding can never be executed as a script.
§S-10 — serving, not just storing
Every file-serving endpoint — this one, backup downloads, generated report files — resolves what to send by looking up a database id (the photo's owning student/teacher row, the backups.id row) and reading that record's stored path server-side. None of them ever accept a raw filename or path fragment from the request. A URL like ?file=../../../config.php has nothing to act on, because there is no "file" parameter that ever reaches the filesystem directly.
Alternative
Store as BLOBs in MySQL — a single-file backup story, but bloats ordinary dumps and slows unrelated queries.

12 · One database vs. one per academic year

Proceeding
Recommend
A single database; every year-scoped table carries academic_year_id. Closed years become read-only at the application layer, not by physical separation.
Reason
A student's full multi-year history needs a plain join, not a cross-database query; backup/restore also stays "one file, one operation."
Alternative
One schema per year — perfect isolation, but no easy "show this student across years" query, and N schemas to manage.

13 · Concurrent edits

Proceeding
Recommend
Optimistic concurrency — reject a save with "this record changed, please reload" if updated_at moved since the form opened. No pessimistic row locking.
Reason
This is a handful of staff on one school LAN, not a high-contention system; locking would add complexity disproportionate to the actual risk.
Alternative
Pessimistic "checked out by X" locks — more correct under heavy contention, unnecessary at this scale.

14 · Installation model

Proceeding
Recommend
A first-run web Setup Wizard — environment check, DB connection test, schema install + seed data, school profile, first admin, first academic year.
Reason
The brief explicitly rules out manual database editing for a non-technical administrator.
Alternative
Ship a raw schema.sql + README — much simpler to build, fails the target-user bar outright.

System Architecture

A layered, plain-PHP MVC. Every request takes the same path; every layer has one job.

Cross-cutting concerns

§S-4 — the install model itself was the vulnerability. Item 28's own installation model is "copy the whole project folder into htdocs." Under XAMPP's default Apache config, everything under htdocs is web-servable unless told otherwise — meaning database/backups/*.sql (password hashes, every student's name/DOB/religion/phone) and storage/uploads/* would sit at a guessable, browsable URL for anyone on the same LAN, the instant the admin follows the documented install steps exactly as written. A properly configured Apache vhost pointing at public/ only would prevent this, but requiring that from a non-technical admin contradicts the entire "just copy to htdocs" premise. Fix, mandatory, zero-configuration: the package ships a .htaccess at the project root containing Require all denied (Apache 2.4, XAMPP's bundled version) that blocks every request that isn't rewritten through public/, plus a second one specifically in public/ that re-allows access there. This works under the exact "copy the folder, done" install model — no vhost edit required — and needs AllowOverride All for htdocs, which is XAMPP's own default. Pointing Apache's DocumentRoot at public/ via a proper vhost remains the ideal, offered as an optional hardening step for a school with IT support (§N), not a requirement.
Section D تصميم قاعدة البيانات

Database Design

Normalized, relational, no comma-separated ID fields anywhere. Sixteen relational entities plus four standalone support tables.

Why student_enrollments exists

The students table holds only biographical facts that don't change with the school year — name, date of birth, religion. Everything year-specific (grade, class, status) lives in student_enrollments, one row per student per academic year. Promotion never edits an existing enrollment; it closes the current one (status = 'promoted') and inserts a new one for the next year, linked back via previous_enrollment_id. This is the mechanism that satisfies "never blindly overwrite historical data" in item 3 — the student's entire academic history is a chain of enrollment rows, not a single mutated record.

There is exactly one sanctioned, logged exception: the single-student Undo Promotion action (§I.1 step 9), which reopens a just-created promotion's source row back to active and deletes the just-created, zero-activity target row it produced — available only immediately after that specific promotion and only while nothing else has touched either row. Every other status transition is one-way. While a row is active, exactly one field may change outside promotion: class_id, via the mid-year reassignment action in §I.9.

Index & constraint strategy

  • Every foreign key is indexed (MySQL does this automatically) plus explicit composite indexes on student_enrollments(academic_year_id, class_id) and teacher_assignments(academic_year_id, teacher_id) — the two hottest report queries.
  • students(status) and activity_logs(created_at)/activity_logs(user_id) indexed for filtering and audit lookups.
  • Reference tables (grades, subjects, classes, academic_years, teachers, students) use ON DELETE RESTRICT — nothing with active children can be hard-deleted; archive instead.
  • Pure join tables (teacher_subjects, role_permissions) use ON DELETE CASCADE — the relationship, not the entity, disappears.
  • Character set & collation are explicit, not inherited. The database and every table are created with CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci stated in the migration file itself — never left to whatever XAMPP's bundled MariaDB happens to default to. Added in §O-8: a default of plain utf8 or latin1 silently mis-stores or mis-sorts Arabic text, and the failure is invisible until someone notices garbled names months later.
  • No hard-delete route exists in the UI for students, teachers, classes, subjects, grades, academic_years, or users — only archive/deactivate. ON DELETE RESTRICT stops orphaning, but it does not stop permanently deleting a row that happens to have zero current children while still being named in historical activity_logs — added in §O-10.

Migration & install strategy

Numbered, additive SQL files in database/migrations/001_*.sql … 0NN_*.sql. A small PHP runner reads a migrations bookkeeping table, applies whatever hasn't run yet — each file inside its own transaction — and records it. database/seeds/ holds idempotent seed scripts (roles, permissions, default subjects/grades, the first academic year) using INSERT ... ON DUPLICATE KEY UPDATE by unique code, so re-running setup never duplicates data. The Setup Wizard (decision #14) is simply the UI in front of "run pending migrations, then run seeds."

Section I سير العمل

Business Workflows

The six processes where getting the exact sequence wrong would either lose data or produce a wrong staffing number. Written as the step-by-step a service class will actually follow.

I.1 · Student promotion

  1. Select source and target year.
    Source is the active or a recently-closed year; target is a year that already exists and has already been through year rollover (§I.4) so its classes exist before promotion runs.
  2. System proposes defaults.
    Every active enrollment in the source year is listed, grouped by grade/class, each pre-assigned to the next grade by sort_order.
  3. Admin marks exceptions.
    Per student or per whole class: repeat (same grade again, same grade_id on the new enrollment), graduate (final grade — forced when a grade has no defined successor), or one of two distinct leaving states corrected at the Final Gate (§S-5) — transferred (left for another school) or withdrawn (left school entirely / destination unknown). Both leaving states skip creating a new enrollment; which one is recorded is now an explicit admin choice, not a single conflated "transfer out (withdrawn)" option as originally drafted — the two carry genuinely different meaning for enrollment-drop reporting.
  4. Admin assigns target classes.
    Bulk ("all of 2A → 3A") or left unassigned for manual placement later; capacity is shown but only soft-warns, never blocks.
  5. Preview.
    One table: every affected student, old grade/class/status → new grade/class/status, with summary counts (promoted / repeated / graduated / transferred).
  6. A promotion lock is acquired.
    Added in §O-17: before the batch starts, the service takes an app-level mutex (a single row/flag, not a DB table lock) so a second admin can't start a second promotion batch against the same source year concurrently. Released when the batch finishes or fails.
  7. Confirm → transaction.
    For each student: close the current enrollment (status set to promoted/repeated/graduated/transferred); for promoted/repeated students, insert a new student_enrollments row in the target year with previous_enrollment_id pointing back. One activity-log entry summarizes the whole batch — not one row per student.
  8. Commit or roll back.
    Any failure rolls back the entire batch; nothing is left half-promoted. A student who already has an enrollment in the target year (e.g. the batch ran twice) is skipped with a friendly note, not a fatal error for the whole run.
  9. Correcting a mistake.
    Added in §O-12, tightened at the Final Gate (§S-12): a narrow "Undo promotion" action, gated by the same students.promote permission as running a batch, lets the admin revert a single student — the source-year enrollment reopens to active, and the target-year row Undo just produced is deleted outright (not status-flipped — it never should have existed and carries zero dependent activity). Available only immediately after that promotion and only while nothing else has touched either row; this is the single sanctioned exception to §D's enrollment-immutability rule (§S-7), and the one correction path that doesn't require running an entire second promotion batch to fix one student.

I.9 · Mid-year class reassignment — added at the Final Gate §S-6

A real, ordinary need the original blueprint never gave a legitimate outlet for: moving a currently-enrolled student from one class to another within the same grade and year — class rebalancing, a scheduling conflict, a parent request — without it being a promotion. Gated by the same students.edit permission Staff already hold (this is routine, not administrative), the action updates exactly one field on the student's current-year enrollment: class_id, and only while status = 'active'. The new class_id must belong to the same grade_id and academic_year_id as the enrollment already has — enforced by the same composite foreign key (§S-1) that protects promotion, so a mis-scoped reassignment fails at the database, not just the form. Logged in activity_logs like every other consequential action. This is the only routine path that touches an active enrollment outside promotion — it exists so staff never have a reason to ask a developer to "just update it in the database."

I.2 · Backup — corrected by audit §O-4

  1. Admin clicks "Back Up Now."
    Manual only in v1 — no scheduled/automatic backups (out of scope; see §G).
  2. Dump schema, then data, in dependency order.
    Corrected: the original plan streamed data only. BackupService now writes each table's CREATE TABLE statement and its data, in a fixed dependency-safe order — reference tables first (schools, roles, permissions, role_permissions, grades, subjects, academic_years, settings), then users, then teachers/students, then classes, then student_enrollments/teacher_assignments/teacher_subjects/subject_staffing_requirements, then activity_logs/backups/login_attempts. Rows still stream in chunks (e.g. 500 at a time) — the database is never held in memory at once.
  3. Finalize the file.
    Renamed to school_backup_YYYY-MM-DD_HHmm.sql, written with a leading signature comment that records the schema/migration version it was taken from — -- NIZAM-BACKUP v1 schema=0027 — so a restore can detect a version mismatch instead of silently applying an incompatible file.
  4. Append a checksum.
    Added at the Final Gate (§S-8): a trailing -- CHECKSUM=<sha256> line, computed over everything written before it. This is the only way to catch a file truncated or corrupted after the fact (an interrupted copy to a USB drive, a bad download) — before replay starts, not mid-way through a DDL statement that can't be undone (§I.3).
  5. Record the outcome.
    A backups row is written either way — status='success' with file size, or status='failed' with the partial file deleted and the technical reason logged (never shown raw to the admin).

Why the schema is included now: a data-only dump assumes the live schema already matches — true today, but not guaranteed after months of migrations. A schema-inclusive dump can restore onto a freshly imaged PC with nothing but Apache and MySQL installed, without first hand-running migrations in the right order.

I.3 · Restore — corrected by audit §O-5

  1. Upload & validate.
    Extension must be .sql; size checked against upload_max_filesize; the first bytes must contain the app's own NIZAM-BACKUP signature and a recognized schema version; the trailing checksum (§O-4/§S-8) is recomputed and compared — a mismatch (truncated upload, corrupted copy) is rejected right here, before any DB work starts, not discovered mid-replay.
  2. Explicit warning.
    States the exact consequence in plain language ("this replaces all current data with the contents of this file") and requires a typed confirmation phrase, not just an OK button.
  3. Automatic emergency backup.
    Runs the full I.2 procedure against the current database, tagged type='pre_restore', before anything is touched. This backup — not a database transaction — is the real safety net (see below).
  4. Replay with foreign-key checks suspended.
    Corrected: the original plan said "replay inside a transaction," which is not actually possible here — see the note below. The replay instead runs with SET FOREIGN_KEY_CHECKS=0 for the duration (reset to 1 automatically when the connection closes, even on failure), so the dependency order from the backup file is a safety convention, not a hard requirement.
  5. Validate structural sanity before declaring success.
    After replay, confirm at least one active Administrator user exists and at least one academic year exists. Extended at the Final Gate (§S-9): also spot-check the composite-FK invariants from §S-1/§S-2 with a direct query (any enrollment or assignment whose class doesn't share its own grade/year) — disabling FOREIGN_KEY_CHECKS for the replay means MySQL/MariaDB will not retroactively validate existing rows once checks are re-enabled, so a corrupted dump could otherwise import silently. Any of these checks failing treats the restore as failed even though the SQL itself executed without error.
  6. Report the outcome.
    Success: activity log entry, confirmation message, forced re-login. Failure: the admin is told plainly what happened and pointed at the pre-restore emergency backup from step 3 to recover — never told "nothing was changed," which this design can no longer guarantee (see below).
Why restore cannot be "one atomic transaction." MySQL/MariaDB DDL statements (CREATE TABLE, DROP TABLE, ALTER TABLE, and — in InnoDB — TRUNCATE) each cause an implicit commit and cannot be rolled back. A restore that recreates tables from a schema-inclusive backup (§I.2) is therefore never fully reversible by a SQL ROLLBACK alone, no matter how the code is written. The actual protection is the mandatory pre-restore emergency backup: if a restore fails partway, the admin recovers by restoring that file, not by relying on an in-flight rollback that MySQL cannot provide. Where the replay is data-only (tables already match the current schema), row deletion uses DELETE rather than TRUNCATE specifically so that portion stays inside a real, rollback-capable transaction — but the guarantee still stops at the first DDL statement.

I.4 · Academic-year activation, closing & rollover — extended by audit §O-11

Create
Label + start/end dates. §O-11: creating a new year now offers "Start from previous year" — a YearRolloverService clones every active class from the outgoing year into the new year (same grade, name, capacity — new rows, since classes is scoped by academic_year_id) and clones every active teacher_assignments row onto the matching new class. The admin edits this starting point (reassign teachers, change periods, add/remove classes) before promotion runs — nothing is locked in by the clone.
Activate
Setting a year's is_active=1 deactivates the previous active year in the same transaction, and is additionally guaranteed at the database by the unique generated-column index from §O-2 — exactly one active year, ever, even under a bug or a race.
Close
Blocked (§S-3) unless zero enrollments in that year still have status='active' — checked live, before the flip, with a plain count and a plain message ("42 students still have unresolved enrollments — run promotion first") rather than a database error. Only once that count is zero does the action set is_closed=1, after which the service layer rejects any INSERT/UPDATE against student_enrollments, teacher_assignments, or classes scoped to that year.
Reopen
A separate, permission-gated, logged action flips is_closed back to 0 — never implicit, never a side effect of another operation.

§S-3 — why the guard is necessary: promotion writes to the source year's enrollments (closing each one to promoted/repeated/etc.) — exactly the write a closed year rejects. Without this guard, an admin who closes the outgoing year before promotion finishes would permanently strand every remaining active enrollment: promotion could never write to it again short of reopening the year, and reopening doesn't retroactively make "close the year, then promote" the safe order it looked like. The one hard rule that makes any admin ordering safe: promotion always precedes closing its own source year, and the guard above is what actually enforces that rather than merely recommending it.

§O-11 — why this matters: the original blueprint described promotion (§I.1) moving students into a target year's classes, but never described how those classes come to exist. Without rollover, every new year starts with zero classes and zero teacher assignments, and an admin would have to hand-recreate the entire class list and every assignment before promotion could even run — the single biggest practical blocker found in the original plan.

I.8 · Archiving a student or teacher — added by audit §O-13

Archiving is the only deletion path exposed anywhere in the UI for students, teachers, classes, subjects, grades, academic years, and users (§O-10) — there is no "delete" button for these entities, ever. Archiving a student or teacher who has an active enrollment or assignment in the current year is not a bare status flip: in the same transaction, StudentService/TeacherService also closes that current-year enrollment or assignment (status = 'withdrawn' / 'archived'). Without this, a report that joins on enrollment status could still list an archived student as if they were present, while a report that checks the student's own status column would correctly exclude them — two reports quietly disagreeing about the same student.

I.5 · Weekly workload calculation

WorkloadService, per teacher per explicitly specified year (O-23 — never "all years combined"): total = SUM(weekly_periods) WHERE status='active' across that teacher's teacher_assignments, also grouped by subject and by class. expected_weekly_capacity is read from that year's own academic_years.expected_weekly_capacity column (§S-11), not the live global setting; difference = total − expected. Highest / lowest / average are computed across all active teachers in the year for the dashboard and the workload report (§K).

I.6 · Staffing shortage calculation

Per subject per year: shortage = required_teachers (subject_staffing_requirements) − COUNT(DISTINCT teacher_id) WHERE subject_id=? AND status='active'. Positive means understaffed; zero or negative means adequately staffed. A subject with no configured requirement is excluded from the shortage report — it is not silently treated as "requires zero teachers."

    Runs every pending migration (§D) inside the wizard, then the idempotent seed scripts (roles, permissions, default subjects/grades).
  4. School profile.
    Name (Arabic + English), logo, address, phone — written to the single schools row (decision #6).
  5. First academic year.
    Label and start/end dates; created and activated in one step.
  6. Administrator account.
    Username and password for the first login — created with the Administrator role, no default/blank credentials ever shipped.
  7. Done — and locked.
    Redirects straight to login and writes a setup.completed marker. Every subsequent request to any /setup/* route checks that marker first and redirects to login if it's set — no exceptions, no in-app "redo setup" button. Re-entering setup mode after go-live requires an explicit file-system or CLI action, never a page reachable by an unauthenticated visitor.

§O-6 — why this matters: the original plan described the wizard's happy path only. Two gaps: (1) closing the browser between steps 3 and 6 left no described way to resume — the wizard now re-derives its position from what's actually true in the database (migrations applied? an admin user exists?) rather than tracking its own separate progress flag, so refreshing or reopening it always resumes at the right step; (2) an unguarded /setup route reachable after go-live is a backdoor that lets anyone on the LAN create a new Administrator account with zero authentication — the lockout above closes that.

Pre-Implementation Architecture Audit

A critical, production-readiness pass over §A–§N — not a summary of them. Thirty-five findings across the twenty required audit areas: 10 CRITICAL, 9 HIGH, 13 MEDIUM, 3 LOW. Every CRITICAL and HIGH finding has already been folded back into §B–§N above (look for the §O-N tags); this section is the record of why, not a duplicate of the fix itself.

O.1 · Database integrity and normalization

O-1 · settings.key is a reserved SQL word

Critical
Current design
The settings table used a column literally named key.
Problem
KEY is a reserved word in MySQL/MariaDB — every reference needs backtick-quoting or the query errors.
Why it matters
One unquoted reference — a hand-written debugging query, a future developer unaware of the reservation — breaks or throws a syntax error in a table every module reads from.
Recommended solution
Rename the column to setting_key.
Alternative
Backtick-quote key everywhere, forever — fragile, depends on every future query remembering the reservation.
Blueprint change
Applied — §D settings table now reads setting_key.

O-9 · Teacher qualification vs. teacher assignment is undecided

Critical
Current design
teacher_subjects (qualification) and teacher_assignments (actual duty) exist as two separate tables with no described relationship between them.
Problem
Nothing stops assigning a teacher to a subject they have no listed qualification for, and no decision was ever made on whether that should be allowed.
Why it matters
Real schools genuinely use substitute teachers outside their primary subject — a hard database gate would block a legitimate scenario, but leaving the rule totally undecided invites different developers to implement conflicting assumptions later.
Recommended solution
Application-layer soft validation: AssignmentService checks the pairing against teacher_subjects and warns, but never hard-blocks.
Alternative
A BEFORE INSERT trigger that hard-enforces qualification — correct for the common case, actively wrong for legitimate substitute coverage.
Blueprint change
Applied — §D teacher_assignments now states the soft-check rule explicitly.

Otherwise, §D's schema holds up: every table is already in third normal form, no comma-separated ID fields exist anywhere, and the students / student_enrollments split (§D's own rationale) is the correct normalization for year-scoped vs. year-independent facts.

O.2 · Foreign keys, indexes, unique constraints, and delete behavior

The RESTRICT/CASCADE split in §D is sound, but it was doing more rhetorical work than it can actually do — see O-10 below. Composite unique constraints (enrollment-per-year, assignment-per-class-per-year, class-name-per-grade-per-year) are all correctly modeled. No new CRITICAL/HIGH finding beyond O-10 (filed under O.11, where it more precisely belongs) and O-22/O-25 in the medium table.

O.3 · Academic-year isolation and historical data preservation

The student_enrollments lineage chain is the right mechanism, and closed-year write-blocking is correctly scoped. Two things needed tightening: the active-year invariant itself (folded into O-2, filed under O.1 since it's fundamentally an integrity constraint) and what "preserved" means when biographical data changes (see medium findings O-26/O-27) — both addressed below rather than repeated here.

O.4 · Student promotion edge cases

O-3 · student_enrollments.status has no 'graduated' value

Critical
Current design
§I.1 describes a final-grade student as forced to "graduate," but §D's ENUM only listed active, promoted, repeated, transferred, withdrawn.
Problem
A direct inconsistency between the documented workflow and the schema meant to support it — attempting to record a graduation would fail outright.
Why it matters
Caught now, this costs nothing. Caught after Phase 3, it's a migration plus a review of every statement that already assumed the old enum list.
Recommended solution
Add 'graduated' to the ENUM.
Alternative
A separate boolean "graduated" flag instead of an enum value — adds a second field every graduation-aware query must also check, no real benefit.
Blueprint change
Applied — §D ENUM corrected.

O-12 · No correction path for a single mis-promoted student

High
Current design
Promotion was described purely as a one-way batch with no undo.
Problem
Fixing one student promoted into the wrong section required running an entire second promotion batch, or a direct SQL edit.
Why it matters
This is a routine admin slip, not a rare edge case. A system with no small-scale undo pushes staff toward exactly the manual database editing item 29 exists to prevent.
Recommended solution
A narrow "Undo promotion" action per student, available only while the new enrollment has no dependent activity yet.
Alternative
No undo — document a manual SQL fix procedure for developers. Reintroduces the manual-editing problem for a routine mistake.
Blueprint change
Applied — §I.1 gained an explicit step 9.

O-17 · Two admins could run promotion for the same year at once

High
Current design
No concurrency guard around the promotion batch itself (only per-record optimistic concurrency, decision #13, was specified — a different scenario).
Problem
A second promotion batch starting mid-way through the first could interleave writes against the same source-year enrollments.
Why it matters
Promotion is rare and whole-school in scope — a race here corrupts far more data at once than a single-record edit conflict ever could.
Recommended solution
A simple app-level mutex (one flag row) held for the duration of a promotion batch.
Alternative
Rely on the per-student UNIQUE(student_id, academic_year_id) constraint to fail the second batch's duplicate inserts — technically prevents corruption, but produces a confusing wall of individual errors instead of a clean "a promotion is already running" message.
Blueprint change
Applied — §I.1 gained an explicit step 6.

O.5 · Teacher qualification vs. teacher assignment rules

Covered fully as O-9 under O.1, where the underlying integrity question actually lives — filed here for the audit checklist's sake, not repeated.

O.6 · Weekly workload and staffing-shortage calculations

Both formulas (§I.5/§I.6) are correct as specified. Two implementation-discipline notes carried to the medium table rather than blocking anything: calculations must always take an explicit academic year (O-23), and aggregates must be computed in SQL, not a PHP loop per group (O-24).

O.7 · Backup correctness

O-4 · Backup was data-only, with no guaranteed table order

Critical
Current design
BackupService listed tables (effectively via SHOW TABLES) and streamed INSERT statements only.
Problem
A data-only dump can't restore onto a database whose tables don't exist yet, and the table order wasn't guaranteed to respect foreign-key dependencies during replay.
Why it matters
A backup is only as good as its ability to actually restore — discovering this gap during a real disaster is the worst possible moment.
Recommended solution
Schema-inclusive dump (CREATE TABLE + data) written in a fixed, dependency-safe table order, with the schema/migration version embedded in the file's signature comment.
Alternative
Data-only dump plus a hard requirement that restore only ever targets a database on the exact same migration version — offers no disaster-recovery path onto a blank machine.
Blueprint change
Applied — §I.2 rewritten.

O.8 · Restore correctness and MySQL/MariaDB transaction/DDL risks

O-5 · Restore cannot actually run "inside one transaction"

Critical
Current design
§I.3 originally claimed the whole replay ran in a transaction that would fully roll back on any failure.
Problem
MySQL/MariaDB DDL (CREATE/DROP/ALTER TABLE, and InnoDB TRUNCATE) auto-commits — none of it can be rolled back. The original claim was flatly incorrect for a schema-inclusive restore.
Why it matters
Trusting this claim in code would mean a partial DDL failure mid-restore leaves the database half-migrated while the app believes — and tells the admin — that "nothing was changed." That's a false promise at the exact moment the admin most needs an accurate one.
Recommended solution
Reframe the safety model: the mandatory pre-restore emergency backup (already planned) is the actual recovery mechanism, not an in-flight rollback; data-only steps use DELETE (transactional) instead of TRUNCATE; SET FOREIGN_KEY_CHECKS=0 for the replay's duration rather than depending on dump order alone.
Alternative
Forbid schema-inclusive restores entirely, requiring the exact same schema version every time — simpler, but reopens the O-4 disaster-recovery gap.
Blueprint change
Applied — §I.3 rewritten with an explicit risk-note explaining why.

O.9 · Setup Wizard failure/recovery behavior

O-6 · No resumability, and no lockout after go-live

Critical
Current design
The wizard was described as a linear happy path with no stated behavior for an interrupted run or for what happens to the wizard route after setup finishes.
Problem
(1) Closing the browser mid-wizard had no described recovery. (2) Nothing stopped /setup from staying reachable and functional after go-live.
Why it matters
(1) Bricks first-run for exactly the least technical user the brief protects most. (2) Is a live authentication bypass — anyone on the LAN could later create a new Administrator account with zero credentials.
Recommended solution
Derive the wizard's position from actual database state (migrations applied? an admin exists?) rather than a separate progress flag; write a setup.completed marker and gate every /setup/* route behind it, permanently, after completion.
Alternative
Protect /setup with a one-time install token deleted after use instead of a completed-marker gate — functionally similar, marginally more moving parts.
Blueprint change
Applied — §N wizard steps rewritten.

O.10 · ID generation and collision risks

O-7 · The ID-numbering scheme had a race condition

Critical
Current design
Decision #10 implied computing the next sequence number as MAX(seq)+1 in application code.
Problem
Classic read-then-write race: two near-simultaneous "add student" requests can compute the same "next" number.
Why it matters
A collision either fails a UNIQUE constraint (a confusing error for a staff member who just wanted to add a student) or, without that constraint, silently issues two students the same code.
Recommended solution
Insert the row first — MySQL's own AUTO_INCREMENT is atomic — then UPDATE that same row's code using its own new id. No separate counter, no race.
Alternative
A dedicated per-year counter table with SELECT ... FOR UPDATE row locking, only needed if the school insists numbering resets to 1 each academic year.
Blueprint change
Applied — §B decision #10 rewritten.

O.11 · Archive vs. permanent deletion semantics (and academic-year rollover, filed here as the other must-fix structural gap)

O-11 · New academic years start with zero classes and zero assignments

Critical
Current design
§I.1 described promotion moving students into a target year's classes; nothing described how those classes come to exist for the new year.
Problem
classes is (correctly) scoped by academic_year_id, so a brand-new year genuinely starts with zero class rows and zero teacher assignments — there is nowhere for promotion to place a student until someone manually recreates the entire class list.
Why it matters
This is the single biggest practical blocker found in the whole blueprint: as written, the promotion feature cannot function at the one moment per year it's needed, because its precondition was never built.
Recommended solution
A YearRolloverService, run when a new year is created, that clones the outgoing year's active classes and teacher assignments into new rows for the new year as an editable starting point.
Alternative
Require the admin to manually recreate every class and assignment each year — technically works, is the exact "excessive workflow complexity" item 18 warns against.
Blueprint change
Applied — §I.4 retitled and extended with the rollover step.

O-10 · No entity ever had hard-delete explicitly ruled out

High
Current design
ON DELETE RESTRICT was treated as "the" protection against destructive data loss.
Problem
RESTRICT only stops deleting a row that still has children. It does nothing to stop permanently deleting a row with zero current children but real historical significance — e.g. a teacher with no active assignments but named in old activity-log entries.
Why it matters
A "temporarily convenient" hard-delete button on an old record could silently erase the subject of past audit-log entries — undermining the accountability item 16 exists to guarantee.
Recommended solution
Never expose a hard-delete action in the UI for the core entities (students, teachers, classes, subjects, grades, academic years, users); archive is the only path. RESTRICT remains a secondary database-level net, not the primary control.
Alternative
Allow hard-delete, but only via a DBA connecting directly to MySQL, entirely outside the application — already effectively true; needed stating as explicit policy rather than left implicit.
Blueprint change
Applied — §D index/constraint strategy gained an explicit bullet.

O-13 · Archiving didn't say what happens to the student's active enrollment

High
Current design
Archiving a student or teacher was described as a status flip on their own record only.
Problem
No described handling for a current-year active enrollment or assignment left dangling after the parent record is archived.
Why it matters
A report joining on enrollment status could still list an archived student as present, while a report checking the student's own status field correctly excludes them — two reports silently disagreeing about the same student.
Recommended solution
Archiving closes the current-year enrollment/assignment in the same transaction as the archive action itself.
Alternative
Leave it to every report to join both tables and filter on both statuses — correct only if every report author remembers to, every time.
Blueprint change
Applied — new §I.8.

O.12 · Authentication, authorization, CSRF, XSS, session security, and local-LAN threats

O-16 · Login throttling only keyed on username+IP

High
Current design
Lockout triggered per (username, IP) pair after too many failures.
Problem
Spreading guesses across many different usernames from one IP never trips any single username's lockout.
Why it matters
Closes an account-enumeration path that the per-username design left wide open, at negligible extra cost.
Recommended solution
A secondary, higher-threshold IP-wide cool-down (e.g. 20 failures across any usernames from one IP within 15 minutes) alongside the existing per-username+IP lock.
Alternative
CAPTCHA after N failures — the brief explicitly bans bypassing/relying on CAPTCHAs for an offline admin tool with no external service to verify against; not viable here.
Blueprint change
Applied — §C Authentication row.

O-19 · CSRF comparison must be constant-time

High
Current design
"Verified in middleware" — no comparison method specified.
Problem
A plain ==/=== string comparison leaks timing information an attacker could in principle exploit to guess the token byte-by-byte.
Why it matters
Cheap to get right, easy to get wrong by default in plain PHP with no framework enforcing it.
Recommended solution
Always compare with hash_equals().
Alternative
None reasonable — this is a one-line fix with no real trade-off.
Blueprint change
Applied — §C CSRF row.

O-18 · Upload hardening needed more than re-encoding

High
Current design
Decision #11: MIME/extension whitelist plus re-encoding images on upload.
Problem
Re-encoding alone is one layer; a stored file still keeps its original name and is served by Apache guessing its content type from the extension.
Why it matters
Defense in depth matters most exactly where a single control might have a flaw nobody's found yet.
Recommended solution
Random generated filenames; a controller that serves the file with an explicitly-set Content-Type; an .htaccess in the uploads folder disabling PHP execution outright.
Alternative
Store uploads entirely outside the web root, proxied through a controller for every request — stronger still, but adds a real request-path cost for something a folder-level execution lockout already neutralizes.
Blueprint change
Applied — §B decision #11.

Residual, not-fully-fixable risk carried to the medium table: session cookies can't carry the Secure flag over the plain HTTP a LAN-only XAMPP install typically uses (O-31).

O.13 · Offline dependency completeness, including fonts and third-party assets

O-15 · "mPDF has RTL support" was never turned into a bundled asset

High
Current design
Decision #3 named mPDF for its Arabic/RTL capability.
Problem
mPDF ships a limited default font set; without explicitly bundling and registering an Arabic-shaping font, it silently falls back to boxes/tofu instead of Arabic glyphs.
Why it matters
"The library supports it" and "the deliverable actually renders it" are different claims — this is exactly the kind of gap that surfaces as a Phase 7 surprise instead of a Phase 2 checklist item.
Recommended solution
Name the exact asset: Amiri-Regular.ttf/Amiri-Bold.ttf bundled under vendor-assets/fonts/ and registered in mPDF's config, as a Phase 7 checklist line item.
Alternative
Noto Naskh Arabic or Cairo — any properly-licensed, properly-shaping Arabic font works; Amiri is simply well-established and freely licensed for embedding.
Blueprint change
Applied — §B decision #3.

O.15 · Concurrent editing

O.16 · Import/export safety

O-14 · Bulk student import (brief item 33) was never scoped

High
Current design

Problem
A genuine, silent gap against the original brief, which explicitly asks for CSV/Excel import "where practical," with mandatory preview and validation if built.

Section P القرارات المعمارية النهائية

Final Architecture Decisions

Every decision implementation must follow, consolidated from §B and corrected by §O. If Phase 3 code conflicts with anything here, the code is wrong, not this list — per the brief's own rule (item 40), a real conflict gets raised for discussion, not silently worked around.

Backend & architecture

  • Hand-rolled lightweight MVC — front controller, router, PSR-4 autoload — not a framework (decision #1).
  • Composer for development only — vendor/ shipped populated; the school never installs anything (decision #2).
  • Single school per installation — a schools table exists for the profile row (name/logo on reports), not as a multi-tenancy boundary (decision #6, client-confirmed 2026-09-06).
  • Bulk student import is out of scope for v1 — manual entry only; revisit post-launch (O-14).
  • No timetable/scheduling module — weekly_periods is a count, not a calendar (O-29).

Database

  • utf8mb4 / utf8mb4_unicode_ci, stated explicitly in every migration — never inherited from server defaults (O-8).
  • settings.setting_key, not key (O-1).
  • student_enrollments.status includes 'graduated' (O-3).
  • Exactly one active academic year, enforced by a generated-column unique index — not application logic alone (O-2).
  • A new academic year clones the previous year's classes and teacher assignments as an editable starting point (O-11).
  • Teacher-subject qualification is a soft, warn-not-block check at the service layer (O-9).
  • No hard-delete route, anywhere in the UI, for students, teachers, classes, subjects, grades, academic years, or users — archive only (O-10).
  • Archiving a student or teacher closes their current-year enrollment/assignment in the same transaction (O-13).
  • IDs derive their numeric part from the row's own AUTO_INCREMENT id, assigned after insert — never a pre-computed MAX+1 (O-7); numbering does not reset per year in v1.
  • Migrations are forward-only; there is no scripted rollback beyond restoring a backup (O-30).

Security

  • Login throttling is per-username+IP and a secondary, higher-threshold IP-wide cool-down (O-16).
  • CSRF tokens compared with hash_equals() only (O-19).
  • Uploads: random filenames, explicit Content-Type on serve, PHP execution disabled in the uploads folder, plus re-encoding (O-18, decision #11).
  • The Setup Wizard is permanently locked behind a setup.completed marker the moment it finishes — no exceptions (O-6).
  • Session cookies cannot carry Secure over plain HTTP on an unmanaged LAN — documented residual risk; a self-signed HTTPS vhost is offered as optional, not required (O-31).

Backup & restore

  • Backups are schema-inclusive (DDL + data), written in a fixed dependency-safe table order, signature-tagged with a schema/migration version (O-4).
  • Restore is protected by a mandatory pre-restore emergency backup — not by a SQL transaction, which cannot fully wrap DDL in MySQL/MariaDB (O-5).
  • Restore validates structural sanity (at least one active Administrator, at least one academic year) before declaring success, in addition to the file's header signature.

Reporting & offline assets

  • Arabic-shaping font files (Amiri or equivalent) are bundled and registered in mPDF explicitly — not assumed from "mPDF supports RTL" (O-15).
  • Exported PDF/Excel column order and date format follow the same reading-order discipline as on-screen RTL tables, set explicitly per export (O-32).

Every other decision in §B (backend framework choice, PDF/Excel/chart libraries, one-database-for-all-years, concurrent-editing model, installation model) stands as originally written — the audit found no reason to revisit them.

Database

  • Every CREATE TABLE states CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci explicitly.
  • Every write goes through PDO prepared statements. No string-concatenated SQL, anywhere, ever — not even for a "trusted" internal value.
  • No column is named key, order, group, or any other SQL reserved word.
  • No business-rule validation (ranges, positivity) lives in a CHECK constraint — validate in the service layer (O-22).
  • Every migration is forward-only and idempotent-safe to re-run; no down() scripts (O-30).
  • A hard-delete SQL statement against a core entity table is only ever run by a human DBA outside the application — the application itself never issues one.
  • student_enrollments and teacher_assignments reference classes through the composite foreign keys in §S-1/§S-2 — never a plain single-column class_id FK, which would let grade or year drift out of sync with the referenced class.
  • Closing an academic year first counts remaining active enrollments in it and refuses if that count is nonzero (§S-3) — never a bare UPDATE academic_years SET is_closed=1.

PHP

  • Controllers validate input shape and delegate — no business logic, no SQL, in a controller.
  • All SQL lives in repositories. Services never construct queries directly.
  • One class per file, PSR-4 autoloaded, PSR-12 style.
  • Every multi-step write that touches more than one table runs inside an explicit transaction, with the specific exception of restore's DDL steps, which cannot be (O-5) — that exception is documented in the code, not silent.
  • ID generation always follows the insert-then-update-own-id pattern (O-7) — never a pre-computed MAX+1.

Frontend

  • No CDN reference of any kind, anywhere in shipped HTML/CSS/JS — Bootstrap, jQuery, Chart.js are vendored files in public/assets/vendor.
  • Every reusable UI element (table, form, modal, pagination, filter bar, empty state) is built once as a component (§L) and reused — never copy-pasted per module.
  • RTL is re-ordered, not mirrored: column order, not just text-align, changes with direction (§C).
  • Every table's pagination request is capped server-side regardless of the requested page size (O-25).

Security

  • CSRF tokens are compared with hash_equals(), never == (O-19).
  • Login throttling checks both (username, IP) and IP-alone thresholds (O-16).
  • Every output goes through the e() escaping helper — no raw variable echoes in a view, ever, including report templates (§S-13) — a student's free-form notes field or an admin-set report footer is exactly as untrusted as any other user input before it reaches HTML that mPDF will parse.

Offline

Backup & restore

  • Backups are schema-inclusive, dependency-ordered, checksum-appended, and signature-tagged with a schema version (O-4, §S-8).

Final Pre-Implementation Gate

§A–§R re-read as one system, not as seventeen independent sections — specifically hunting for contradictions between them. Seventeen findings: 4 BLOCKER, 8 HIGH, 2 MEDIUM, 3 LOW. Every BLOCKER and HIGH finding is already corrected back into §B–§Q above (tagged §S-N) and cross-checked against every section it touches.

A. Student enrollment integrity

S-1 · An enrollment's grade/year could disagree with its own class

Blocker
Current design
student_enrollments carried grade_id, class_id, and academic_year_id as three independent single-column foreign keys.
Problem
Nothing enforced that the enrollment's own grade_id/academic_year_id actually matched the grade_id/academic_year_id of the classes row named by class_id — exactly the "Grade 3 enrollment pointing at a Grade 2 class" scenario named in this gate's brief.
Why it matters
This is the single row every report, every promotion calculation, and every dashboard count reads to know "what grade is this student in." An impossible combination here doesn't stay contained — it silently corrupts every downstream number.
Recommended solution
Keep grade_id on the enrollment (it must remain independently readable for the unassigned-class state after promotion), but enforce agreement with a composite foreign key: FOREIGN KEY (class_id, grade_id, academic_year_id) REFERENCES classes(id, grade_id, academic_year_id), backed by a new UNIQUE (id, grade_id, academic_year_id) on classes. NULL class_id (unassigned) is simply not checked, by ordinary FK semantics — exactly the case that must stay legal.
Alternative
Drop grade_id from student_enrollments entirely, deriving grade only through class_id — clean in theory, but breaks the moment an enrollment is promoted-but-unassigned, since then there would be no class row to derive the grade from at all.
Blueprint change
Applied — §D classes and student_enrollments tables.

B. Teacher assignment integrity

S-2 · An assignment's class could belong to a different year

Blocker
Current design
teacher_assignments carried class_id and academic_year_id as two independent single-column foreign keys.
Problem
Identical shape to S-1: nothing stopped a row naming academic_year_id = 2026 while class_id pointed at a class that actually belongs to 2025.
Why it matters
Workload and staffing-shortage calculations (§I.5/§I.6) are entirely dependent on assignments being correctly year-scoped — a single cross-year assignment silently inflates one year's workload numbers and understates another's.
Recommended solution
FOREIGN KEY (class_id, academic_year_id) REFERENCES classes(id, academic_year_id) — covered by the same composite unique index added for S-1.
Alternative
Application-layer validation only (check on save) — correct for the happy path, but offers no protection against a direct data-layer bug or a future developer bypassing the service layer.
Blueprint change
Applied — §D teacher_assignments table.

C. Academic-year lifecycle

S-3 · Closing a year could permanently strand un-promoted students

Blocker
Current design
§I.4 described closing a year as a simple flag flip; §I.1 described promotion as writing status changes onto the source year's enrollments. Nothing connected the two.
Problem
The stated lifecycle order (create → roll over → promote → verify → activate → close) is only safe if promotion always runs before closing — but nothing enforced that order. An admin closing the source year first (a plausible, even natural-seeming click, "the year is over, let's close it") would then find promotion itself blocked, since promotion needs to write to the very enrollments the closed year now protects.
Why it matters
This is exactly a "workflow that attempts to modify data that should already be immutable/closed" turned into a dead end rather than a guardrail — the students concerned would be trapped with no clean path forward except reopening the year, which doesn't retroactively fix the ordering problem.
Recommended solution
"Close" first counts remaining active-status enrollments in that year and refuses, with a plain count, if any remain. This makes the correct order the only order that succeeds, rather than a convention the UI merely suggests.
Alternative
Warn but allow closing anyway ("42 students unresolved — close anyway?") — leaves the same trap available on purpose, just with a confirmation step in front of it; rejected as too easy to click through under end-of-year time pressure.
Blueprint change
Applied — §I.4.

D. Promotion / repetition / transfer / graduation

S-5 · "Transferred" and "withdrawn" were conflated in the workflow

High
Current design
§D's ENUM correctly listed both transferred and withdrawn as distinct values, but §I.1's own workflow text described a single option: "transfer out (withdrawn, no new enrollment)."
Problem
A duplicated/conflicting business rule in the sense the gate asked to hunt for: two enum values exist, but the one place that's supposed to explain when each applies never actually distinguished them — different staff members would record the same real-world event under different statuses with no guidance.
Why it matters
Enrollment-drop reporting (a real registrar concern — transfers-out vs. drop-outs are administratively distinct categories) becomes meaningless if the two statuses are applied inconsistently.
Recommended solution
State the distinction explicitly as two separate admin-selectable options: transferred (left for another school) and withdrawn (left entirely / destination unknown).
Alternative
Collapse to a single status and drop the distinction — simpler, but throws away real reporting value for no technical benefit.
Blueprint change
Applied — §I.1 step 3.

S-6 · No legitimate path existed for an ordinary mid-year class move

High
Current design
The only thing that could ever change a student's class_id was the once-a-year promotion batch.
Problem
Real schools need to move a currently-enrolled student to a different section mid-year — class rebalancing, a scheduling conflict — and nothing in the blueprint gave staff a sanctioned way to do it.
Why it matters
A missing legitimate path for a routine need is exactly what pushes staff toward asking a developer to "just update it in the database," undoing the entire "no manual database editing" principle for something that should be a two-click, logged, everyday action.
Recommended solution
A narrow "Reassign class" action, gated by students.edit, touching only class_id on an active enrollment, constrained to the same grade/year by the S-1 composite FK.
Alternative
Require a full withdraw-and-re-enroll to move a student — technically avoids adding a new action, but destroys the enrollment's continuity for what is genuinely a same-year, same-grade change, not a real re-enrollment.
Blueprint change
Applied — new §I.9.

S-7 · Enrollment immutability was implied, never stated as a rule

High
Current design
No screen was ever described that would let staff freely edit a past enrollment — but nothing explicitly forbade one being added later, either.
Problem
An unstated rule is not a rule a future developer (or future session of this same assistant) is bound by — "we never described an edit screen" is silence, not a guarantee.
Why it matters
This is the exact category the gate named directly: "workflows that attempt to modify data that should already be immutable/closed." The enrollment chain is the system's entire historical record — it needs an explicit, written invariant, not an absence of counter-examples.
Recommended solution
State it directly: once status leaves active, a row is never edited by any general-purpose action, full stop, with exactly one named, logged, narrowly-scoped exception (Undo Promotion, S-6's sibling in §I.1).
Alternative
Enforce it only at the database level (e.g., a trigger rejecting updates to non-active rows) — more bulletproof, but heavier than this system needs given the rule is already enforced by simply never building an edit screen for it.
Blueprint change
Applied — §D student_enrollments.

Final-year graduation was re-checked directly: a graduating student's last enrollment carries status='graduated', produces no new row, and its full previous_enrollment_id chain remains queryable forever under the immutability rule above — confirmed consistent, no further finding.

E. Backup and restore

S-8 · Nothing detected a truncated or corrupted backup file before replay

High
Current design
§I.2/§I.3 (post-§O) validated a header signature and a schema version, but nothing checked whether the file's actual bytes were complete and unaltered.
Problem
A file truncated by an interrupted copy to USB, or otherwise corrupted, could pass the header check and begin replaying — and since DDL can't be rolled back (§O-5), a failure discovered mid-replay is strictly worse than one caught before it starts.
Why it matters
Corruption detection was explicitly named in this gate's brief, and the cost of catching it upfront versus mid-disaster is the entire difference between "the restore was refused" and "the database is now half-migrated."
Recommended solution
Append a SHA-256 checksum line to the backup file, computed over everything before it; verify it during upload, before any DB work starts.
Alternative
Rely on MySQL's own SQL-syntax error if a truncated file breaks mid-statement — catches some truncation, but only after DDL has likely already run, and never catches a file corrupted in a way that's still syntactically valid SQL.
Blueprint change
Applied — §I.2, §I.3.

S-9 · Disabling FK checks during replay could let corrupted data in silently

High
Current design
§O-5's fix runs replay with SET FOREIGN_KEY_CHECKS=0; §O-5's structural check afterward only confirmed an admin and an academic year exist.
Problem
MySQL/MariaDB do not retroactively validate existing rows when FOREIGN_KEY_CHECKS is turned back to 1 — so a corrupted dump that violates the new S-1/S-2 composite-FK invariants could import cleanly and stay silently wrong.
Why it matters
The two composite FKs exist specifically to prevent impossible enrollment/assignment states — a restore path that can bypass them without detection would quietly reopen the exact hole they were built to close.
Recommended solution
Extend the post-replay structural check with a direct query for any enrollment or assignment whose class doesn't share its own grade/year — treat any hit as a failed restore.
Alternative
Re-enable FOREIGN_KEY_CHECKS mid-replay after each table instead of at the very end — doesn't help, since MySQL still never scans pre-existing rows retroactively; the explicit query is the only real check.
Blueprint change
Applied — §I.3.

Everything else re-checked clean: schema+data completeness, dependency ordering, and MariaDB/MySQL syntax compatibility were already addressed at §O-4/§O-5/§O-8, and hold up under this second pass. utf8mb4_unicode_ci specifically (rather than MySQL 8's default utf8mb4_0900_ai_ci, which MariaDB doesn't have at all) is what makes a dump portable between the two — worth restating here since this gate's brief asked for it directly.

F. Security

S-4 · The mandated install model exposes backups and student data on the LAN

Blocker
Current design
§C's file structure kept database/, storage/, etc. as siblings of public/, with storage/ merely annotated "never web-served directly."
Problem
The brief's own installation model is "copy the whole project folder into htdocs." Under XAMPP's default Apache config, everything under htdocs is web-servable unless told otherwise — so following the documented install steps exactly as written would put every backup (password hashes, every student's name/DOB/religion/phone) and every uploaded file at a guessable, browsable LAN URL.
Why it matters
This is the most severe finding in either gate: total, silent exposure of every student's personal data and every account's password hash to anyone on the same network, caused by following the installation instructions correctly rather than by misconfiguring anything.
Recommended solution
Ship a deny-all .htaccess at the project root (Require all denied), which works under the exact "copy the folder, done" install model with no vhost edit required — XAMPP's default AllowOverride All on htdocs is what makes this sufficient.
Alternative
Require the admin to configure an Apache vhost pointing at public/ — the textbook-correct fix, offered here as an optional hardening step for a school with IT support, but not viable as the only protection given the non-technical target user.
Blueprint change
Applied — §C.

S-10 · File-serving routes had no explicit path-traversal rule

High
Current design
Upload-side hardening (random filenames, execution lockout, O-18) was specified; nothing was said about how a backup download or generated report is served back.
Problem
A naive download endpoint that takes a filename or path from the request is a classic path-traversal vector, explicitly named in this gate's security checklist.
Why it matters
Cheap to prevent by construction, expensive to discover after the fact.
Recommended solution
Every file-serving route resolves its file by a database id, looked up server-side — never a client-supplied filename or path fragment.
Alternative
Sanitize/validate a client-supplied path (reject .., resolve and confirm it stays inside the expected folder) — works if implemented perfectly every time; resolving by id removes the entire attack surface instead of policing it.
Blueprint change
Applied — §B decision #11.
